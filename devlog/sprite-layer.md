# OBJ 精灵层的硬约束

通路选型: **静态预渲染 BG + 角色走 8bpp OBJ 硬件合成**。合成是 PPU 做的, CPU 成本为零 ——
这是"一屏六只"能成立的前提。代价是 GBA 在这条通路上有几条不留余地的硬约束, 每一条都
踩过一次。

## 1. 竖形 32×64 对象, 这台模拟器一个像素都不画

近档要放大到 26×56 的内容, 精灵框就得是 32×64。GBA 的 OBJ 尺寸编码里 (0,2) = 32×64
是合法组合, 真机认, **但本项目的 mGBA 0.9.3 在 Mode 4 下对竖形对象不画任何东西** —— 没有
报错, 没有半张图, 就是空白。

所以 `obj_place()` 把 32×64 一律拆成上下两个 32×32 方形对象:

```c
int half  = h >> 1;
int names = (w * half) / OBJ_TILE_BYTES;      // 半张占多少个 name (32x32 就是 +32)
obj_set_dim(slot,     base_name,      x, y,       prio, w, half, bank);
obj_set_dim(slot + 1, base_name + names, x, y + half, prio, w, half, bank);
if (flip_x) { /* 两半各自翻同一个 FLIP_X 位 */ }
```

镜像是左右翻, 所以上下两半的**顺序不变**, 只各自加同一个 `OBJ_A1_FLIP_X`。
代价是多一个 OAM 槽(128 槽上限)和一次名字偏移。

## 2. "隐藏对象"不能只靠 objMode

想关掉一条不该画的扫描线时, 只设 `objMode = 2`(affine)不够: 实测 mGBA 在 Mode 4 下照常
把它画出来, 而 attr0 的低 8 位被清零等于把 Y 挪到 0 —— 通关/死亡屏因此多出一块 32 宽的
头肩(GAME OVER 帧上 x 104..120, y 1..30, 344 个亮像素)。真机认 objMode=2 且屏外坐标不画。
**两边一起写才成立**: 既设 objMode, 也把对象挪到屏外停车场坐标。

## 3. 8bpp 精灵只有一张 256 色调色板

Mode 4 下 OBJ 读 `0x05000200..0x050003FF` 这 512 字节 = **连续 256 项, 一张表**。不是
"每个对象 16 色 × 16 组"。所以多个角色必须**共用索引区间**:

| 区间 | 归属 |
|---|---|
| 0 | 透明(硬件语义, 不能当颜色用) |
| 1–223 | 丧尸纹理(256 色回归版, 32×64) |
| 224–255 | 主角平直色 |

只写前 128 项会怎样? 索引 200 变全黑 —— 这条是实测出来的, 不是文档推的。
`tools/reserve_obj_palette.py` 负责把 224–255 折叠进纹理换出来的空位。

## 4. 图块顺序: 行主序, 而且可以离线反解

1D 映射下 `字节偏移 = name × 32`, OBJ 字符区从 `0x06010000` 起, 本项目用 names 512..1023
= 16 KB(丧尸 224 names + 主角 96 = 320)。`obj_pack_dim()` 的图块顺序是**从左到右、从上
到下**(行主序), 不是硬件文档里另一种说法的列主序。

这条实测验证过: 用同帧的 OAM + VRAM + objpal 自己合成一张图, 和 shot 逐像素比 ——
行主序 **99.9% 通道差 ≤ 2**, 列主序只有 95.8%。差的 0.1% 是 5bit→8bit 的取整方式。

它的价值不止于"打包写对了": 任何离线分析(对比度、透明掩码、脚线位置)都可以直接从
`.oam.bin` + `.vram.bin` 反解出精灵像素, **不必在 ROM 里加插桩**。[效果页](/showcase) 的
对比度表就是这么量的。

## 5. 脚线口径: 内容底行 = 框底 − 2

`obj_place()` 里 `y = feet - h`, 所以"精灵框底行"= `feet - 1`, 屏幕上的可见脚线 =
`feet - 3`。这个口径能成立, 靠的是把每个格子的**内容底行**钉在框底 −2:

```c
static const u8 zt_below_init[3] = { 15, 14, 14 };   // 下标 = NEAR / MID / FAR
```

`zs_below` 是"满档时投影中心到脚"的像素数, **必须按档给**。近档换 32×64 后面配额是 758
(中远 416), 脚被完整画出来了; 沿用 14 会让内容底行正好落在框底, 破口径 2px。改焦距或
重烘动画后要重量 —— 它错几 px, 那一档的脚就整体飘几 px。

投影本身是线性的(s=480 量到 53 行 / s=512 量到 56 行, 与 28×1.875、28×2 对得上),
飘的只有"脚离中心多远"。

## 6. 姿态缓存: 把渲染挪出每帧通路

每个 `(精灵块, 朝向桶, 姿态)` 格子在进场预热时**实时渲一次**, 结果按 OBJ 最终布局存进
EWRAM; 之后运行时只做一次 32 位 DMA 换入。

| 量 | cyc | 说明 |
|---|---|---|
| 近档一格实时渲染 | **1,267,727** | 32×64 / scale 512 / 758 面 |
| 中档一格 | **484,361** | 32×32 / scale 208 / 416 面 |
| 远档一格 | **424,051** | 32×32 / scale 168 / 416 面 |
| 一次 1 KB 换入 DMA | **2,299** | 比渲染便宜 **235 倍**(中档口径) |

朝向用 5 个桶 `{0,32,64,96,128}`(8 位角, 45° 一圈)+ `OBJ_A1_FLIP_X` 覆盖 8 个八分位 ——
模型左右近似对称, 用接触表逐格核对过。

一个反直觉的推论:**近档单格 1,267,727 已经是 30fps 预算 559,240 的 2.3 倍**。所以"这一迭代
填完会不会超预算"这个填充判据必须改成"每迭代最多填一格", 否则近档冷平面永远填不上,
动画会**静默冻结**且没有任何报错。卡顿可以恢复, 冻结不行 —— 详见
[周期测量页](/devlog/perf)。

## 7. 名额与降档

每档常驻块数 `zt_slots = {1, 1, 4}`。同档挤进多于块数的实体必须**整体降一档**, 不降的话
两只抢同一块, 后渲的把先渲的像素盖掉, 两只共用同一张图。降档选"该档里最远的那只", 所以
近景名额永远留给最近的实体: 同屏最多 1 只上前。

滞回状态记的是**原始档**而不是降完的档 —— 否则输掉名额的那只每帧被拽回近档 → 每帧换档 →
每帧重渲, 分组彻底失效。

## 8. 影子 OAM 晚一个迭代才上屏

第 2 节修的是"隐藏没生效"。同一页后来又长出第二个精灵残留, 症状几乎一样 —— 玩家站在
"YOU ARE DEAD" 上面 —— 原因完全不同: **隐藏生效了, 只是晚一帧。**

节拍器在循环顶:

```c
while (1) {
    vsync();
    obj_commit();          /* 影子 OAM -> 0x07000000 */
    ...
    if (gameover_t > 0) { obj_hide_from(0); render_gameover(); }
}
```

`obj_commit()` 发布的是**上一次迭代**写的影子。这一次迭代 `obj_hide_from(0)` 改的 128 条
影子要等下一次循环顶才进 OAM, 于是死亡/通关的**第一个硬件帧**照旧画旧精灵。玩法态每迭代
吃 2 个硬件帧, 所以只要切换发生在迭代里, 这一帧谁都躲不掉。

修法 = 两个分支各补一次提交。结算页是静态页, 多一次 1 KB DMA 付得起:

```c
obj_hide_from(0);
obj_commit();     /* 不补这一句, 死亡第一帧玩家站在字上面 */
```

代价量过, 不是推的(这一对是 **B5 → B6**): 群戏基准稳态 **20,752 cyc/硬件帧**、进场预热 **111,672,571 cyc**
两项**逐位不变**(这两条分支基准态不走), ROM text 473,632 → **473,640 B**, 差额正好是
两条 `bl`。玩法态帧 340 与修前**逐字节相同**。修前后同一帧的像素账在
[数字总表 → 玩法态实拍](/data) 那一节。

值得一提的是它**怎么被发现的**: 不是读代码, 是那张欠了两轮的"玩法态实拍"。补截图时顺手让
主角挂机挨打, 数了一下死亡切换帧的非黑像素 —— 1,141, 而结算页稳定后只有 120。这一轮之前
我把这类多出来的亮像素判成"背景没填完的残帧"(依据是等 20 帧后就干净了), 方向错了。
区分两者看**包围盒**: 残帧的亮像素铺满整屏, 精灵残留永远是一条钉在固定列上的竖条
(这次是 y40–103 / x108–131)。像素数只能告诉你"有东西", 包围盒才能告诉你"是什么东西"。
