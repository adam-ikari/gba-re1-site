# 房间背景的提取与落位

"跑在真房间里"是这一轮图像工作的全部前提。黑幕基准能证明周期数, 但证明不了"丧尸站在
地板上"。

## 1. 背景不在 ROM 文件系统里, 而且在压缩容器内

RE:DS 的场景背景是 **2D 预渲染图**(不是实时 3D), 但它们不在 NDS 文件系统的可见位置,
而在 `/data/cpac_stage1..9,a..i,mg.bin` 这 20 个 Capcom 容器内, 并且**压缩存放**。

裸扫 `BTX0` 魔数在 stage1 能命中 265 处, 但块头字段位置随压缩漂移(ROOM1000 的长度字段
落在 +9 而不是 +8), 魔数后面紧跟的是压缩流, 直接喂 ndspy 会报 `Incorrect NSBTX TEX0 magic`。

这里推翻过一条自己的结论:"BTX0 是非标准 NSBTX 变体、离线解包走不通"。**是错的** ——
ndspy 4.2 的 NSBTX 认的就是 `BTX0`(assert numblocks==1, TEX0 固定在 0x14)。卡点是压缩,
不是魔数。

## 2. 三级流水线

```
tools/room_extract.py   533 页 / 503 房间 / 17 个区域码   (切割+解压交给 apicula, Rust)
tools/room_grade.py     打分筛
tools/rooms2gba.py      裁 240x160 + 量化 255 色 + 索引右移 -> src/generated/rooms_gba.c
```

抓屏路线(`tools/room_capture.py` + desmume)不再是必需, 只在需要"游戏里那一帧的确切明暗"时用。

## 3. 房间页有两类, 分数高不等于能站人

容器里两类页面混在一起, manifest 里长得一模一样:

- **整张预渲染背景** —— 透视已经在图里, 一屏 256×192;
- **碎片页** —— 楼梯、书架、扶手这些独立几何的贴图, 内容是一块块四边形散在黑底上。

判据在非黑掩码(亮度 > 6)上算:

```
score = fill * (1 - holes) * min(span_w, span_h)
```

实测 503 个房间里 `score ≥ 0.7` 只有 **19** 个, ≥ 0.5 有 48 个, ≥ 0.3 有 104 个。
**能直接当背景的完整视图是少数**, 大部分房间还需要网格 + UV 才能合成。

## 4. 地板在哪, 是美术知识不是像素统计

试过一条看起来必然成立的路: 从背景图反推地板线(按色相找木地板)。

**否掉了。** 同一套色相判据在 f080 上暖色占比 0.96(整幅都是暖色木墙, 地板和墙分不开),
在 ROOM3040 上 0.047。判据在两个房间上朝相反方向失效。

于是改成人工量: `tools/room_grid.py` 把每张房间图按 3 倍放大、叠 20px 网格、标上坐标,
然后**照着图量**。理由写进工具文档: "地板在哪"是美术知识, 不是像素统计能算出来的。

顺带纠正一条旧笔记: 它写"3040 画面里根本没有地板"。对着 ROM 里这一页重看是错的 ——
**有**, 只是带子很窄(y=140..160, x=0..190)。量的其实是另一页。

## 5. 落位表: 每个房间一张, 缺的房间用编译期报错挡住

黑幕基准里 `cx` 是随便摆的、脚线按档位统一。一旦背景是真房间, 这两件事立刻露馅:
实测洋馆 2F 转角那张, 6 只里 4 只踩在左墙/后墙上; 脚线三档差 8px 在黑幕里看不出问题,
真房间里那 6 只全贴在天花板下方。

```c
typedef struct { u8 cx, feet; } ZsPlace;
#if ZS_ROOM == 0
static const ZsPlace zs_ent_real[ZS_ENT_TABLE] = {
    { 100, 142 },                             /* 近档: 楼梯下段, 最大只 */
    { 138, 126 },                             /* 中档: 同一楼梯右半 */
    {  92, 114 }, { 112, 108 },               /* 远档: 往上收, 贴后沿 */
    { 130, 102 }, { 144,  96 }
};
#elif ZS_ROOM == 2      /* f080: 被光打亮的右下地板 x=105..215 / y=100..160 */
...
#elif ZS_ROOM == 3      /* 3040: 窄地板带 y=140..160, x=0..190 */
...
#else
#error "ZS_ROOM=1 (11A2) 没有落位表: 它是俯拍楼梯, 侧视丧尸精灵站不上去。要用它得先换构图, 别照猫画虎补一张假表。"
#endif
```

三个设计决定:

1. **深度、相位、朝向一个都不动。** 档位与重渲节奏必须与黑幕基准逐位一致, 两边的周期数
   才可比。落位表只允许改横向 `cx` 和脚线。
2. **换房间必须重量一张表。** 房间之间地板位置没有规律可推, 别指望算出来。
3. **没有合适地板的房间宁可编译失败。** 一张假表会安静地给出一个"能跑但全错"的画面,
   比编译错误坏得多。

核对方式不是看图猜: `dump_obj` 出来的 OAM 里每只对象的 `y` 应当**正好等于** `feet − h`。
f080 量到 y = 93/125/99/88/82/75/71,3040 量到 95/127/121/116/114/112/111, 逐个对上。

## 6. 换房是贵的一次性动作

| 量 | cyc | 备注 |
|---|---|---|
| 每帧渲染成本(ROOM1036) | 930,615 | 与黑幕 930,599 差 **16 cyc**(0.002%) |
| 一次性 `mode4_load_frame` | **528,184** | = 30fps 预算 559,240 的 **94%** |

**背景内容不影响每帧成本** —— face/span/顶点计数逐位相同, 贵的是换房那一次整屏灌入。
所以换房必须藏在黑幕淡入淡出里, 不能连续切。

(930,615 是"每帧都实时渲染"那一版的数; 当时的稳态是 20,736 cyc/迭代 —— **B2/B3 时代读数**, 出货口径 **B8** 那颗复测 20,357(现出货 B11 的群戏与 B8 逐位相同), 见
[周期测量页](/devlog/perf)。两者的差正是姿态缓存的价值。)
