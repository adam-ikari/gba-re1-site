# 调色板: 索引 0 与那张唯一的 256 色表

GBA 在 Mode 4 下只有一个 256 色 BG 调色板(`0x05000000..0x050001FF`)和一个 256 色 OBJ
调色板(`0x05000200..0x050003FF`)。整个画面的颜色预算就是这 512 字节。所有调色板相关的
坑都从这一句推出来。

> **并排比较的图已从这一页撤下嵌入** —— 页面只放单幅画面, 每张仍标 `B#` 归属。撤下的文件都在仓库里,
> 线上 `/img/<名字>.png` 仍可取(未做物理删除), 完整清单与理由见 [数字总表 → 版本登记](/data#版本登记)。

## 1. 索引 0 必须空着 —— 而且修法不能在运行时

运行时 `setup_role_palette` 把 `PALMEM[0]` 强制成纯黑。理由: 清屏(`dma_fill32(page, 0, ...)`)
和 `draw_dim_bar`(暗条)都写索引 0, 这是"任何背景下都保证是黑"的**唯一一格**。

房间素材如果量化时用满 256 格, 落在索引 0 的像素就会被改色。实测 ROOM1036 有 **88 个像素**
踩在这格上, 而那格的原始色是 `0x73FD`(近白)。于是截图顶部出现一块"不该存在的黑块" ——
最初的判断是"精灵越界回绕", **误判**。

修法在素材侧, 不在运行时:

```
tools/rooms2gba.py / tools/img2mode4.py
  量化到 BG_COLORS - 1 = 255 色, 然后把索引整体右移一格 -> 索引 0 恒为空
```

代价几乎为零(ROOM1036 整图 MAE 1.337 → 1.338), 还顺带修好了大厅背景
(mansion_hall MAE 1.799 → 1.313, 那 109 个黑洞本来就是错色)。

**为什么不在运行时绕开**(比如让暗条用别的索引): 暗条要的是"与房间调色板无关的确定黑",
而 0–223 每一格都可能是房间里的任意颜色 —— 这条约定曾经用"写死 16 号"实现, 换一次素材
它就跳成卡其色。

## 2. 8bpp 精灵只有一张表, 多角色必须共用索引区间

这条的完整推导在 [OBJ 精灵层](/devlog/sprite-layer#_3-8bpp-精灵只有一张-256-色调色板)。
结论: 丧尸占 1–223, 主角占 224–255, 0 是硬件透明。

"只写前 128 项"会发生什么? 索引 200 变全黑 —— 也就是说 Mode 4 的 OBJ 调色板**不是**
16 组 × 16 色的结构, 而是连续 256 项。这条是实测确认的。

## 3. 丧尸纹理从 16 色回到 256 色

走过一段弯路: 为了省内存, 纹理一度量化到 **16 色**(64×128)。省下来的地方很小, 丢掉的地方
很大 —— 16 色撑不起"白衬衫 + 破洞 + 露肉腿"这种同时需要灰阶和暖色的材质, 丧尸在暗色房间
里糊成一团。那张 16 / 256 色板并排的图已撤下嵌入(文件 `/img/pal_16_vs_256.png` 仍可取), 结论不靠它:
撑不起同时需要灰阶和暖色的材质, 而量化省下的是本来就没用满的上限(下一节)。

回归 256 色的实际改动:

| 项 | 改动 |
|---|---|
| 烘焙 | `bake_zombie_textures.py --size 32 --colors 256`(调色板 172 个非零色, 纹理 2×2048 字节 8bpp 索引) |
| 渲染器 | `ZB_TEX_W=32 / ZB_TEX_H=64`,UV 采样 `u>>5 / v>>6`(原 `u>>6 / v>>5` 对应 64×128) |
| EWRAM | `MODEL_MAX_FACES` 2048 → **1024**(`tri_buf` 省一半;场景实际最大面数 758 < 1024, 安全) |

**省 EWRAM 是靠砍一个从来没用满的上限, 不是靠降颜色数。** 这条顺序很重要: 先查上限是不是
虚设, 再考虑牺牲画质。

## 4. 验证链: Python 全模拟是主证据

改调色板/采样位这类事, 在模拟器上验证会被"环境本身慢"骗到(见
[周期测量页](/devlog/perf) 开头那条)。当时的做法:

- Python 完整模拟一次 64×64 渲染 → 丧尸 358 px、bbox `x[24,39] y[16,48]`、
  **107 种非零调色板色**(> 16 就证明 256 色真的生效了), 轮廓(头/躯干/腿)正常;
- 与离线烘焙帧的色差降到 **8.6**;
- 模拟器截图只用来确认"没有花屏", 不用来判画质。

## 5. 顺带: 为什么背景是静态 BG 而不是每帧重画

早期走的是 Mode 3 整屏软渲染通路(背景 + 角色都靠 CPU 写), 每帧要重灌整屏背景。换成
"静态预渲染 BG + 角色走 OBJ 硬件合成"之后, 合成的 CPU 成本变成 **0**(两条通路的画面并排图已撤下嵌入,
文件 `/img/mode3_vs_mode4.png` 仍可取)。

代价是 Mode 4 只有 256 色、且 OBJ 只有 128 个槽 —— 也就是前面所有约束的来源。
