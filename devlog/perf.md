# 周期测量装置与成本表

## 为什么必须自己数周期

最初的性能判断是"mGBA 里画面刷得很慢, 所以 GBA 模拟极慢"。这是错的: mGBA 在
`Xvfb` + 软件 GL 下, 每帧整屏重绘的**宿主**开销被误读成了被测对象的开销。

要回答"真机能不能到 30 FPS", 只有一个可信指标: **GBA 周期数**。墙钟、FPS 计数、
截图刷新的快慢, 都不是证据。

## 计数器: TM0/TM1 级联 32 位

`src/perf.cpp`:

- TM0 = `TM_FREQ_1 | TM_ENABLE` → 每个 GBA 周期 +1
- TM1 = `0x0004 | TM_ENABLE`(cascade)→ TM0 溢出时 +1
- `perf_now() = (TM1 << 16) | TM0`:1 周期分辨率, 量程 2³² ≈ 256 秒
- 读法要防进位竞争: 读 TM1 → 读 TM0 → 再读 TM1, 若 TM1 变了就重读 TM0

一次 `perf_now()` ≈ **30 周期**(IWRAM 内)/ ≈ **105 周期**(从 ROM 取指)。所以它适合
"每阶段/每面/每行"的粒度, **不能放进逐像素内层**。这条不是建议, 是量出来的: 打开
`PERF_FINE` 之后, 插桩自己吃掉被测对象的 22%(光栅 1,294,291 → 插桩后 1,517,249,
2,654 次 `perf_now`)。

## 读出通道: mGBA 自带的命令行调试器

```bash
SDL_VIDEODRIVER=dummy SDL_AUDIODRIVER=dummy mgba -d build/re1demo.gba   # stdin 喂命令
break 0x08001A98      # perf_dump 的地址 (arm-none-eabi-nm -C re1demo.elf 取)
continue
x/4 0x030011CC        # 从 perf_val 起, 每行 4 个字
quit
```

`SDL_VIDEODRIVER=dummy` 是关键: 不建窗口 → 不经过 X / 软件 GL → 核心以近实时跑。
上面这一整套已经封装成一条命令:

```bash
python3 tools/read_perf.py run --rom build-xxx/re1demo.gba --elf build-xxx/re1demo.elf --frames 900
```

备选通道都不如它: `-g` 的 gdb stub 在 0.9.3 下 `qSupported` 握手失败、运行中拒绝 `m` 包;
`.sav` 通道要等干净退出才落盘。

## 一个记账 bug, 让所有历史数字虚高 2 倍

`read_perf` 的"CPU 渲染合计"= 5 个粗槽相加。但 `P_VERTS` / `P_RASTER` / `P_BLIT` 是在
`render_zombie_model` **内部**累加的, 而调用它的那段区间也要记账(`P_OTHER`)—— 同一段时间
被数了两遍。2026-10-01 之前 `P_OTHER` 就是"整段区间"的原样计时, 于是:

- 一次 64×64 实时渲染被报成 **3,062,104 cyc / 5.55 FPS**, 真值 **1,557,759 cyc / 10.77 FPS**
- 由它推出的"有 1.57M 未计时项比光栅化本身还贵"是**记账假象**, 不是待查的性能问题。
  真实的"渲染之外"只有 87,961 cyc(打包+DMA 40,948 + 清视口/清 zbuf ≈47,000)= 一次渲染的 5.6%

修法是 `perf_other(t0, inner0)`: 外层区间结束时减掉 `perf_inner()` 在这一段内的增量,
`P_OTHER` 回到它名字的意思(余额)而不是"整段"。**新增任何粗槽计时都必须落在 `perf_inner()`
里**, 否则又会重复计数。

推论两条: 看到"合计"里某项异常大, **先怀疑嵌套再怀疑代码**; 拆价最稳的办法仍是整帧相减
(A/B 构建), 插桩只用于定位。

## "帧"是主循环一次迭代, 而迭代率是状态相关的

主循环顶有一次 vsync, 末尾**还有一次**(玩法年代的历史遗留)。它在同一个迭代里再等一个
整帧, 于是 2026-10-03 之前**任何状态**的真实迭代率都是 29.85 次/秒(2 个硬件帧/迭代),
不是注释里一路写到底的 59.7。

修法 `if (state != ST_ZOMBIE) vsync();` 之后:

- 群戏基准: 实测每 **1** 个硬件帧迭代一次 = 59.7 迭代/秒
- 其余状态(含玩法): 仍每 **2** 个硬件帧一次 = 29.85/秒(玩法的每帧位移量是在这个速率上
  调出来的, 全局删掉会把行走与出拳速度翻倍 —— 那是另一件事)

**这条修正推翻的是换算, 不是周期数。** 历史上每一个 `FPS = 16.78M / cyc` 的数都乐观了
两倍。所以 `cyc/迭代` 永远是迭代率的上界估计, 要真数帧率就用 `tools/peekshot` 盯
`perf_frames` 对硬件帧号, **不要引用 read_perf 打印的那一行 FPS**。

两个门槛不能混(姿态时钟每 2 个迭代走 1 格, 分子是**迭代率**):

| 门槛 | 含义 |
|---|---|
| ≤ 279,620 cyc/迭代 | 1 迭代吃 1 个硬件帧 = 59.7 迭代/s = **姿态率 30Hz** ← 真正的目标 |
| ≤ 559,240 cyc/迭代 | 1 迭代吃 2 个硬件帧 = 29.85 迭代/s = 姿态率 15Hz ← 不掉整帧的下界 |

"满足 30fps 预算"只保证不出现整帧定格, **不保证动画在正确速率上**。

## 成本表(2026-10-05, 近档 32×64 + 运行时姿态缓存)

单位 cyc / **主循环一次迭代**。单价用 `-DZS_ENTS=1/2/3/6` 阶梯量增量、每档增量再除以 31 格
隔离出来的, 不是估的。

| 量 | cyc | 怎么量的 |
|---|---|---|
| 近档一格实时渲染(32×64 / scale 512 / 758 面) | **1,267,727** | `-DZS_ENTS=1` 预热总额 39,299,532 / 31 |
| 中档一格(32×32 / scale 208 / 416 面) | **484,361** | `-DZS_ENTS=2` 增量 15,015,183 / 31 |
| 远档一格(32×32 / scale 168 / 416 面) | **424,051** | (6 只总额 − 2 只总额) / 4 / 31 |
| 一次 1 KB 精灵换入 DMA | **2,299** | 稳态 `P_BLIT` = 2,300/迭代 配 1 次换入/迭代 |
| **群戏基准稳态(0 填充 + 1 换入)** | **20,736**(`B2/B3` 时代读数) | `read_perf run --frames 900` |
| 进场预热一次付清 | **106,897,063 = 6.38 秒** | `tools/peekshot` 读 `zs_warm_cyc` |
| 一次性换房 `mode4_load_frame` | **528,184** | = 30fps 预算的 94%, 必须藏在黑幕淡入淡出里 |
| 1 个硬件帧 | 280,896 | 换算基准 |

稳态 20,736(**B2/B3 时代读数**)= 一个硬件帧的 **7.4%**。出货那颗 ROM 是 **B8**, 2026-10-09 复测
**20,357 cyc/硬件帧 = 7.3%**; 全站早期正文里沿用 20,752 的段落都属 **B4–B7** 那一族(逐张归属见
[版本登记](/data#版本登记))。这就是"六只同屏"的真实处境: 一旦缓存热了, 每帧只剩
一次 DMA 和一次 OAM 写。

### 三条被作废的旧引用

1. **"540,223 = 一次 32×32 的单价"是误记** —— 那是 100,510,644/186 的**整体平均**, 被当时
   仍在实时渲的近档拉高, 不是任何一档的真价。
2. "586,112 = 一格均价" —— 是在 yaw=0 轴置换快路径上隔离量的**单点**。
3. "DMA 约 250 cyc/KB" —— 从来没有隔离实测过。

结论方向不变但倍数要改口: 换入比渲染便宜 **235 倍**(中档口径), 不是 4000 倍。

## 填充判据: 从"不超预算"改成"每迭代最多一格"

近档单格 1,267,727 是 30fps 预算 559,240 的 **2.3 倍**。如果填充判据是"填完不超预算",
**近档永远填不上** —— 冷平面会永久停在最后一次换入的那一格, 动画死掉, 且没有任何报错。

卡顿可以恢复, 冻结不行。所以判据改成"这一迭代还没填过":

```c
static u32 zt_spent;
...
if (zt_spent) return 2;      // 每迭代最多一格
```

对中/远两档而言这与旧判据**逐位等价**(它们本来就低于预算); 只有近档被从"永远填不上"里
救出来。最坏迭代 = 一格: 中/远 ≈ 1.7 个硬件帧, 近档 ≈ 4.5 个硬件帧(75ms 一次)。

验证方式: `-DZS_NO_WARMUP` 构建, 确认缓存确实能从零填到稳态。

## 两条结构性事实

1. **面密度 ≈ 3 px/面** —— `每面/每行 setup` 完全主导成本, 内层循环再优化也省不了多少。
   结论: 必须按像素预算剔除/合并亚像素面(LOD 或分块), 而不是继续抠填充。
2. **ROM 取指罚 6.25×**(2~3 cyc/条)—— 均摊 cyc/操作比指令数理论值高约 5 倍。热点搬
   IWRAM 是有量级依据的, 不是玄学优化。

## 一个会静默骗你的坑

`peekshot` 的符号地址必须从**当次构建**的 `.map` 取。`zs_warm_cyc` 在 build-tallk 是
`0x300293c`、在 build-e1 是 `0x30026dc`; 拿错构建读到的是 `1,039,220,241` 这种荒谬值,
而且**不报任何错**。
