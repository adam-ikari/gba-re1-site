# 周期测量装置与成本表

## 为什么必须自己数周期

最初的性能判断是"mGBA 里画面刷得很慢, 所以 GBA 模拟极慢"。这是错的: mGBA 在
`Xvfb` + 软件 GL 下, 每帧整屏重绘的**宿主**开销被误读成了被测对象的开销。

要回答"真机能不能到 30 FPS", 只有一个可信指标: **GBA 周期数**。墙钟、FPS 计数、
截图刷新的快慢, 都不是证据。

## 计数器: TM0/TM1 级联 32 位

`src/perf.cpp`:

- TM0 = `TM_FREQ_1 | TM_ENABLE` → 每个 GBA 周期 +1
- TM1 = `0x0004 | TM_ENABLE`(cascade)→ TM0 溢出时 +1
- `perf_now() = (TM1 << 16) | TM0`:1 周期分辨率, 量程 2³² ≈ 256 秒
- 读法要防进位竞争: 读 TM1 → 读 TM0 → 再读 TM1, 若 TM1 变了就重读 TM0

一次 `perf_now()` ≈ **30 周期**(IWRAM 内)/ ≈ **105 周期**(从 ROM 取指)。所以它适合
"每阶段/每面/每行"的粒度, **不能放进逐像素内层**。这条不是建议, 是量出来的: 打开
`PERF_FINE` 之后, 插桩自己吃掉被测对象的 22%(光栅 1,294,291 → 插桩后 1,517,249,
2,654 次 `perf_now`)。

## 读出通道: mGBA 自带的命令行调试器

```bash
SDL_VIDEODRIVER=dummy SDL_AUDIODRIVER=dummy mgba -d build/re1demo.gba   # stdin 喂命令
break 0x08001A98      # perf_dump 的地址 (arm-none-eabi-nm -C re1demo.elf 取)
continue
x/4 0x030011CC        # 从 perf_val 起, 每行 4 个字
quit
```

`SDL_VIDEODRIVER=dummy` 是关键: 不建窗口 → 不经过 X / 软件 GL → 核心以近实时跑。
上面这一整套已经封装成一条命令:

```bash
python3 tools/read_perf.py run --rom build-xxx/re1demo.gba --elf build-xxx/re1demo.elf --frames 900
```

备选通道都不如它: `-g` 的 gdb stub 在 0.9.3 下 `qSupported` 握手失败、运行中拒绝 `m` 包;
`.sav` 通道要等干净退出才落盘。

## 一个记账 bug, 让所有历史数字虚高 2 倍

`read_perf` 的"CPU 渲染合计"= 5 个粗槽相加。但 `P_VERTS` / `P_RASTER` / `P_BLIT` 是在
`render_zombie_model` **内部**累加的, 而调用它的那段区间也要记账(`P_OTHER`)—— 同一段时间
被数了两遍。2026-10-01 之前 `P_OTHER` 就是"整段区间"的原样计时, 于是:

- 一次 64×64 实时渲染被报成 **3,062,104 cyc / 5.55 FPS**, 真值 **1,557,759 cyc / 10.77 FPS**
- 由它推出的"有 1.57M 未计时项比光栅化本身还贵"是**记账假象**, 不是待查的性能问题。
  真实的"渲染之外"只有 87,961 cyc(打包+DMA 40,948 + 清视口/清 zbuf ≈47,000)= 一次渲染的 5.6%

修法是 `perf_other(t0, inner0)`: 外层区间结束时减掉 `perf_inner()` 在这一段内的增量,
`P_OTHER` 回到它名字的意思(余额)而不是"整段"。**新增任何粗槽计时都必须落在 `perf_inner()`
里**, 否则又会重复计数。

推论两条: 看到"合计"里某项异常大, **先怀疑嵌套再怀疑代码**; 拆价最稳的办法仍是整帧相减
(A/B 构建), 插桩只用于定位。

## "帧"是主循环一次迭代, 而迭代率是状态相关的

主循环顶有一次 vsync, 末尾**还有一次**(玩法年代的历史遗留)。它在同一个迭代里再等一个
整帧, 于是 2026-10-03 之前**任何状态**的真实迭代率都是 29.85 次/秒(2 个硬件帧/迭代),
不是注释里一路写到底的 59.7。

修法 `if (state != ST_ZOMBIE) vsync();` 之后:

- 群戏基准: 实测每 **1** 个硬件帧迭代一次 = 59.7 迭代/秒
- 其余状态(含玩法): 仍每 **2** 个硬件帧一次 = 29.85/秒(玩法的每帧位移量是在这个速率上
  调出来的, 全局删掉会把行走与出拳速度翻倍 —— 那是另一件事)

**这条修正推翻的是换算, 不是周期数。** 历史上每一个 `FPS = 16.78M / cyc` 的数都乐观了
两倍。所以 `cyc/迭代` 永远是迭代率的上界估计, 要真数帧率就用 `tools/peekshot` 盯
`perf_frames` 对硬件帧号, **不要引用 read_perf 打印的那一行 FPS**。

两个门槛不能混(姿态时钟每 2 个迭代走 1 格, 分子是**迭代率**):

| 门槛 | 含义 |
|---|---|
| ≤ 279,620 cyc/迭代 | 1 迭代吃 1 个硬件帧 = 59.7 迭代/s = **姿态率 30Hz** ← 真正的目标 |
| ≤ 559,240 cyc/迭代 | 1 迭代吃 2 个硬件帧 = 29.85 迭代/s = 姿态率 15Hz ← 不掉整帧的下界 |

"满足 30fps 预算"只保证不出现整帧定格, **不保证动画在正确速率上**。

## 成本表(2026-10-05, 近档 32×64 + 运行时姿态缓存)

单位 cyc / **主循环一次迭代**。单价用 `-DZS_ENTS=1/2/3/6` 阶梯量增量、每档增量再除以 31 格
隔离出来的, 不是估的。

| 量 | cyc | 怎么量的 |
|---|---|---|
| 近档一格实时渲染(32×64 / scale 512 / 758 面) | **1,267,727** | `-DZS_ENTS=1` 预热总额 39,299,532 / 31 |
| 中档一格(32×32 / scale 208 / 416 面) | **484,361** | `-DZS_ENTS=2` 增量 15,015,183 / 31 |
| 远档一格(32×32 / scale 168 / 416 面) | **424,051** | (6 只总额 − 2 只总额) / 4 / 31 |
| 一次 1 KB 精灵换入 DMA | **2,299** | 稳态 `P_BLIT` = 2,300/迭代 配 1 次换入/迭代 |
| **群戏基准稳态(0 填充 + 1 换入)** | **20,736**(`B2/B3` 时代读数) | `read_perf run --frames 900` |
| 进场预热一次付清 | **106,897,063 = 6.38 秒** | `tools/peekshot` 读 `zs_warm_cyc` |
| 一次性换房 `mode4_load_frame` | **528,184** | = 30fps 预算的 94%, 必须藏在黑幕淡入淡出里 |
| 1 个硬件帧 | 280,896 | 换算基准 |

稳态 20,736(**B2/B3 时代读数**)= 一个硬件帧的 **7.4%**。出货那颗 ROM 现在是 **B11**(text 510,324 B,
md5 `6d9a4aa7…`); 下面这个 **20,357 cyc/硬件帧 = 7.3%** 是 2026-10-09 对**口径 B8 那颗**复测的值, B11 只删了
玩法态的主角占位, 群戏那 900 帧窗口的六粗槽合计与 B8 一字不差(10,165,891 cyc), 所以这个稳态对两颗都成立。
全站早期正文里沿用 20,752 的段落都属 **B4–B7** 那一族(逐张归属见
[版本登记](/data#版本登记))。这就是"六只同屏"的真实处境: 一旦缓存热了, 每帧只剩
一次 DMA 和一次 OAM 写。

### 三条被作废的旧引用

1. **"540,223 = 一次 32×32 的单价"是误记** —— 那是 100,510,644/186 的**整体平均**, 被当时
   仍在实时渲的近档拉高, 不是任何一档的真价。
2. "586,112 = 一格均价" —— 是在 yaw=0 轴置换快路径上隔离量的**单点**。
3. "DMA 约 250 cyc/KB" —— 从来没有隔离实测过。

结论方向不变但倍数要改口: 换入比渲染便宜 **235 倍**(中档口径), 不是 4000 倍。

## 填充判据: 从"不超预算"改成"每迭代最多一格"

近档单格 1,267,727 是 30fps 预算 559,240 的 **2.3 倍**。如果填充判据是"填完不超预算",
**近档永远填不上** —— 冷平面会永久停在最后一次换入的那一格, 动画死掉, 且没有任何报错。

卡顿可以恢复, 冻结不行。所以判据改成"这一迭代还没填过":

```c
static u32 zt_spent;
...
if (zt_spent) return 2;      // 每迭代最多一格
```

对中/远两档而言这与旧判据**逐位等价**(它们本来就低于预算); 只有近档被从"永远填不上"里
救出来。最坏迭代 = 一格: 中/远 ≈ 1.7 个硬件帧, 近档 ≈ 4.5 个硬件帧(75ms 一次)。

验证方式: `-DZS_NO_WARMUP` 构建, 确认缓存确实能从零填到稳态。

## 两条结构性事实

1. **面密度 ≈ 3 px/面** —— `每面/每行 setup` 完全主导成本, 内层循环再优化也省不了多少。
   结论: 必须按像素预算剔除/合并亚像素面(LOD 或分块), 而不是继续抠填充。
2. **ROM 取指罚 6.25×**(2~3 cyc/条)—— 均摊 cyc/操作比指令数理论值高约 5 倍。热点搬
   IWRAM 是有量级依据的, 不是玄学优化。

## 一个会静默骗你的坑

`peekshot` 的符号地址必须从**当次构建**的 `.map` 取。`zs_warm_cyc` 在 build-tallk 是
`0x300293c`、在 build-e1 是 `0x30026dc`; 拿错构建读到的是 `1,039,220,241` 这种荒谬值,
而且**不报任何错**。

## 玩法演示与群戏基准合流(2026-10-15 第二十三轮, 演示口径 = **B16**)

裁定是 2026-10-13 定的: 「demo 直接用群戏基准」—— 不再单独养一条玩法渲染通路, 玩家在 6 只
丧尸已经满速跑着的那间餐厅里移动、瞄准、开枪, 演示与出货口径是同一颗。那次只记进了项目 brain
(连同它的原因: 独立玩法通路实测一次迭代 4.37 个硬件帧 ≈ 7 fps), 本站没写过。本轮是它的落地、
计价, 以及三条被它照出来的旧缺陷。

**构建**: `build-r23-dp` = `-DZS_ROOM=4 -DZS_DEMO_PLAY`(`ZS_REAL_SCENE=ON`、`ZB_MIP_LEVELS=1`),
md5 `e042c9ab…`, text **513,724 B**。这条开关在编译期钉了四条断言: 必须开 `ZS_REAL_SCENE`、
必须 `ZS_ROOM=4`(只有餐厅机位标过定)、与 `ZS_DEMO_WALK` 互斥、与 `ZS_BAKED_POSES` 互斥 ——
合流的意义就是走运行时姿态缓存那条路, 烘好的姿态平面没有餐厅的落位表可查。

**开场复验**(规矩: 从 raw 产物重算, 不引用本站自己的结论)。本轮所有对照都挂在今天从当前
HEAD 重烘的那颗 **B15 口径** ROM 上(`9665e85f…`, text 514,672 B): 它的群戏基准帧 900 与站点
登记的 `scene_crowd_b15.png` **逐像素相同(0 / 345,600)**。顺带这就是本轮那三条修法的画面凭证
—— 出货口径的群戏一帧没动, 动的全是"回到 UI 页"那一路。

### 一、节拍: 一次迭代 = 一个硬件帧

| 量 | 演示态(B16) | 怎么读的 |
|---|---|---|
| 进场 | 标题→模式→说明→玩法落在硬件帧 60 / 120 / 180, 预热约 **383** 个硬件帧(期间页上是 LOADING) | `shot` 连拍 + `perf_frames` |
| 稳态迭代率 | **1.00 迭代 / 硬件帧** = 59.7 次/秒 | `perf_frames` 在 hw 700→1500 走 137→937 |
| 稳态单价 | **17,494 cyc / 迭代**(P_BLIT 3,189 + P_OTHER 14,305) | 同窗口, 两段各 400 迭代, 两段读数差 0.02% |
| 对照: 合流之前那条独立玩法通路 | **4.37 硬件帧 / 迭代** ≈ 7 fps | 2026-10-13 立项那次的读数(记在项目 brain, 本站当时没有发过, 见下面第二段) |

节拍器是同一个: 循环顶 `vsync()` + `obj_commit()`, 末尾那次额外 `vsync()` 过去只有 `ST_ZOMBIE`
跳过, 现在 `ST_PLAY` 在演示口径下也跳过。但这**只解释了一半**: 按立项那次建的模型, 旧玩法态
4.26 帧/迭代 = 地板 2 帧(多等的那次 VBlank)+ 一次近档实时渲 1,267,727 cyc 按 `zt_every=2` 摊
下来的 2.26 帧。省掉地板只到 2.26 帧/迭代(≈26 fps); 另一半是**渲染本身换了通路** —— 玩法态那
一只每两迭代重光栅一整格近档平面, 群戏这条稳态每迭代只有一次 1 KB 换入(登记单价 2,299 cyc)
加一次 OAM 写, 光栅根本不在帧内。合流买的从来不是"少等一个 VBlank", 是**不再为一只丧尸重付
整格平面的钱**。
基准那颗本轮重烘的读数是 **20,353 / 20,345 cyc/迭代**(hw 1000→2000、2000→2999 两段), 仍在
已登记的 19,431–20,752 带内, 所以修法没有动到热路。演示比基准便宜 2,851 cyc/迭代, 但**这两个
数不可互推**: 一个态每迭代在算 HUD、准星、输入与命中判定, 另一个态的槽位安排不同, 而本轮没有
做同树 A/B, 所以不把它报成"合流省了多少"。

### 二、可玩性: 逐条走通, 每条都有变量读数

瞄准框是**画在背景页上**的 9×9 方框, 不是精灵 —— 8bpp Mode4 的 OBJ 没有透明索引(索引 0 是一
个颜色), 拿精灵画框就会带一块不透明的底板。每迭代先擦上一格再画新一格。

- **击杀**: 手枪 3 发一只(`dp_hp` 3→0 才清位); Simple 模式火箭炮一发一只, 清场读数
  `dp_mask` 63→31→15→13→5→4→0, `room_cleared` 在第 **1220** 帧置位, 通关页 ZOMBIE DOWN 上
  **没有残留准星**。
- **失败出口是真的**: Normal 只有 12 发, 而 6 只要 18 发 —— 弹药见底就是站着挨到死。本轮实测
  这条: 同一套按键在 Normal 下打到 `dp_mask`=31 就再也推不动(12 发打完), 在 Simple 下能清场。
- **挨打**: 接触判定用**世界坐标**(Δx ≤ 160、Δz ≤ 220, 90 迭代无敌帧), 不用屏幕坐标 —— 6 只
  摊在 66 px 里, 拿屏幕距离当"贴到你了"会让玩家一站定就被深度差 0.14 单位的远档那只打一下
  (第一版实测就是这样)。横扫人群 hp 3→0 在第 **2409** 帧, `gameover_t`=90, 死亡页干净。

图: `public/img/demo_play_b16.png`(帧 920, 餐厅 + 6 只 + 准星)、`public/img/demo_clear_b16.png`
(帧 1400, 通关页)。

### 三、三条缺陷: 一次所有权移交, 归还只做了一半

这是本轮真正的收获 —— 三条里前两条在**共用路径**上, 出货口径同样中。共同形状很清楚:
**某个态把一层的所有权接了过去, 而"还回去"只做了一半**。

1. **背景帧与背景调色板不成对**。`gr_load_bg()` 过去只重灌 `mansion_hall_data`, 而群戏那条
   `zs_paint_bg()` 换的是**整张 256 色** BG 表。于是任何一次"进过房间再回 UI 页"都是满屏错色:
   菜单背景是大厅的索引配餐厅的颜色。B15 那颗按 B 回菜单实测 **31,029 / 38,400 像素**与干净
   菜单不同(平均偏差 36.7), 修后 **0**。图 `public/img/menu_pal_garbled_b15.png` = 修前那颗
   的菜单(字是好的 —— 224-255 那段被 `setup_role_palette` 补过; 糊的是背景)。
2. **UI 页接管显示页时不清 OBJ 层**。菜单与说明页只往背景上写字, 而 OBJ 永远合成在背景之上,
   后果是丧尸站在主菜单里。演示构建实测 **1,103 px** 残留(集中在 x118-188 / y95-151), 修后 **0**。
3. **同一条"背景页被糊过要收回"立了两个标志**。演示自己另立了 `dp_bg_dirty`, 而"从说明页按 A
   回场景"那条路置的是 `gr_bg_dirty`, 没人置前者 —— 说明页 8 行字永久糊在场景里(实测回来那帧
   **31,649 / 38,400 像素**不同)。已并回 `gr_bg_dirty` 这一个标志。

三处都改在共用函数里(`gr_load_bg` / `ui_need_draw`), 都只在**页面切换那一次**付费: 512 B 灌表
+ 128 次 OAM 影子写 + 一次 1 KB DMA。每帧热路一字节没动 —— 上面那句基准 20,3xx 就是这句话的
凭证。

**代价要记账**: 出货口径那颗自今天的 HEAD 重建是 `9665e85f…`, **不再是登记的 B15 `66add72f…`**
(text 514,664 → 514,672 B)。B15 登记的那些数按它自己那颗 ROM 继续成立, 但"从 HEAD 重建 B15
会逐字节一致"这句话以后不能再说 —— 别名锁的是那颗 ROM, 不是源码。

### 保留四条

1. **演示态没有主角形象**。玩法态的主角在 B11 被删掉(那只立方体拼的替身不是主角), 至今是空缺。
   所以"玩法演示"现在演示的是房间、丧尸、射击反馈与结算, 不是主角 —— 主角那张脸是下一条路
   (`em2000` 烘焙管线: glb + BCA → 顶点帧 → 共用 256 色 OBJ 调色板 → 姿态平面, 且要塞进 EWRAM)。
2. **HUD 上那格房间名仍写 "MANSION HALL"**, 而画面是餐厅。改文案要动字库(字体是从实机扫出来的
   子集), 不在本轮范围。
3. **演示与基准那 2,850 cyc/迭代的差不做归因**, 缺同树 A/B。
4. **B16 不进出货竞争**, 按 B13 的先例记作"演示专用·不上产线": 它是最新构建, 但不是「当前画面」。

### 方法论一条

页面所有权要**成对移交**: 谁改了一层, 回来时那一层的每一样东西 —— 帧、调色板表、精灵、脏标志
—— 都得一起还。验"回得去"的办法是拿**进之前那一帧逐像素比**(本轮三处都是 0 / 38,400), 而不是
看一眼觉得"差不多" —— 那三处缺陷每一个用眼睛看都像"菜单本来就是这样的"。
